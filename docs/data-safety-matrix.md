# Todo17 Data Safety Matrix

This matrix documents the implemented Todo17 analytics, consent, and data-lifecycle system (`.omo/plans/android-app-implementation.md`, Todo 17 "분석·보안·데이터 수명주기 강화") as built at HEAD. Every claim cites the exact source file and, where one exists, the test that pins it. Grounded in `docs/초보 식집사_PRD.md` sections 1.1.3, 8.1-8.3, plus the analytics, retention, consent, identification, weather, notification, and account-deletion implementation under `functions/src/`, `core/model/`, `core/database/`, `app/src/main/kotlin/com/planterior/helper/analytics/`, `firestore.rules`, and `storage.rules`.

## 1. Analytics event allowlist (strict, event-name-only)

The wire contract has two nesting levels that must not be confused:

- **Callable batch wrapper** (`recordAnalyticsEvent`): `{ ownerUid, events: [...] }`. `ownerUid` exists only at this outer level and exists purely to let the server assert equality against the authenticated Firebase Auth `uid` (`assertOwner`, `functions/src/analytics.ts:233-238`); it is never trusted as an identity source by itself and never reaches the persisted event document. The Android callable payload literally sends `"ownerUid" to command.ownerUid` alongside `"events"` (`app/src/main/kotlin/com/planterior/helper/analytics/AnalyticsRemoteGateway.kt:117-124`). `events` is bounded to `ANALYTICS_EVENT_BATCH_LIMIT = 50` (`functions/src/analytics.ts:4`).
- **Each event object**, on the wire and in `analyticsEventInputSchema` (`functions/src/analytics.ts:58-65`, `.strict()`), is exactly four fields: `schemaVersion`, `eventId`, `eventName`, `consentRevision`. No other field is accepted; the schema rejects any extra key, and `ownerUid` never appears inside an individual event object.
- **Persisted event** (`StoredEvent`, `functions/src/firestore-analytics-store.ts:55-61`) has exactly five fields: `schemaVersion`, `eventName`, `consentRevision`, `occurredAt`, `expiresAt`. It carries no `uid`/`ownerUid` field at all; ownership is implicit in its Firestore path, `users/{ownerUid}/analyticsEvents/{eventId}` (`functions/src/firestore-analytics-store.ts:229`), never a document field. `parseStoredEvent` enforces this exact key set with `hasExactKeys` (`functions/src/firestore-analytics-store.ts:565-591`).

**Client input contract (per event object):**

| Field             | Type                  | Who sets it                           | Notes                                                                                                                                                                                              |
| ----------------- | --------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`   | literal `1`           | client                                | `analyticsEventInputSchema` rejects any other value (`functions/src/analytics.ts:58-65`)                                                                                                           |
| `eventId`         | client-generated UUID | client                                | `z.string().uuid()`; the same `eventId` reused with a different `eventName`/`consentRevision` is rejected `already-exists` (`sameEvent`, `functions/src/firestore-analytics-store.ts:301-309`)     |
| `eventName`       | enum, 23 values       | client (14 of 23) or server (9 of 23) | closed set via `z.enum(ANALYTICS_EVENT_NAMES)`; CLIENT-eligible names are enforced separately in `executeRecordClientAnalyticsEvents`, which rejects any server-only name with `permission-denied` |
| `consentRevision` | positive safe integer | client or server                      | must equal the authoritative `commandGeneration` at write time or the batch transaction rejects it `failed-precondition` (`functions/src/firestore-analytics-store.ts:259-266`)                    |

**Server-derived fields (never accepted from the client, never present on the wrapper's `events[]` entries):**

| Field                                                | Derived from                                                                                                                                                          |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| owner (Firestore path segment, not a document field) | `request.auth.uid`, asserted equal to the wrapper's `ownerUid` (`functions/src/analytics.ts:233-238`)                                                                 |
| `occurredAt`                                         | server transaction clock at write time (`this.now()`, `Timestamp.now` by default, `functions/src/firestore-analytics-store.ts:281-282`)                               |
| `expiresAt`                                          | `occurredAt + 35 days` (`ANALYTICS_EVENT_TTL_MILLIS`, `functions/src/analytics.ts:3`; stamped in `storedEvent`, `functions/src/firestore-analytics-store.ts:427-439`) |

## 3. Consent model

### 3.1 Default-off, exact-next, no backfill

Implemented in `functions/src/firestore-analytics-store.ts` (`FirestoreAnalyticsStore.setConsent`, lines 82-166) and enforced identically to the pre-existing `consents/location` mechanism.

- **Default-off**: `getConsent` returns `granted: false, commandGeneration: 0` when `users/{uid}/consents/analytics` does not exist (`defaultConsent`, `functions/src/firestore-analytics-store.ts:456-464`). No event can be recorded before the first server-confirmed grant; `recordBatch` throws `failed-precondition` if the consent document does not exist or `granted` is `false` (`functions/src/firestore-analytics-store.ts:248-257`).
- **Exact-next**: every consent mutation carries a `commandGeneration` that must equal `currentGeneration + 1`, or the transaction throws `aborted` "Analytics consent generation changed; reload required" (`functions/src/firestore-analytics-store.ts:118-125`). A resubmission with the same `operationId` and identical `granted`/`commandGeneration` replays the stored receipt idempotently instead of re-mutating (`functions/src/firestore-analytics-store.ts:99-113`); an `operationId` reused with a different payload is rejected `already-exists`.
- **No backfill**: `recordEvents`/`recordServerEvent` reject any event whose `consentRevision` does not equal the current `commandGeneration` at write time (`functions/src/firestore-analytics-store.ts:259-266`), so an event can never be attributed to a consent state that was not authoritative when it occurred.

### 3.2 Immediate local revoke purge

`AnalyticsConsentCoordinator` (`app/src/main/kotlin/com/planterior/helper/analytics/AnalyticsConsentCoordinator.kt`) disables local recording synchronously, before the remote `setConsent` call is even issued: `execute()` calls `local.disableImmediately()` and `local.cancelWorkAndPurge(command.ownerUid)` as the first actions when `command.granted == false` (lines 178-189), and `deletionReceived`/`clearLocalOwner` do the same on account deletion and owner switch (lines 137-150, 152-166). `disableImmediately()` clears the in-memory authorization used by `QueuedProductEventRecorder.record` (`app/src/main/kotlin/com/planterior/helper/analytics/AnalyticsRecorder.kt:49-52`), so any event recorded after that point is silently dropped rather than queued. `AnalyticsDeliveryTask.run` (`app/src/main/kotlin/com/planterior/helper/analytics/AnalyticsWorker.kt:42-58`) independently purges the local Room queue for any owner/UID/consent-revision mismatch before delivering a batch, so an in-flight WorkManager run cannot flush events past a revoke that landed mid-flight. Test: `app/src/test/kotlin/com/planterior/helper/analytics/AnalyticsConsentCoordinatorTest.kt` ("revoke disables and purges").

### 3.3 Server stale-revision denial and purge convergence

- Stale-revision denial: `recordBatch` rejects any event batch whose `consentRevision` does not match the live `commandGeneration`, `failed-precondition` (`functions/src/firestore-analytics-store.ts:259-266`).
- Purge convergence: `setConsent`, when transitioning to `granted: false`, calls `purgeRevokedEvents` (`functions/src/firestore-analytics-store.ts:325-346`), which pages `users/{uid}/analyticsEvents` by `consentRevision <= revokedGeneration` in batches of `ANALYTICS_REVOKE_PURGE_LIMIT = 200` and deletes every page until none remain, bounded by a `ANALYTICS_REVOKE_PURGE_DEADLINE_MILLIS = 45s` wall-clock deadline; if the deadline is hit before convergence it throws `deadline-exceeded` so the caller must retry the exact same revoke command rather than silently leaving events behind (`functions/src/firestore-analytics-store.ts:328-334`). `revokeForAccountDeletion` (`functions/src/firestore-analytics-store.ts:180-200`) drives the same convergence loop as part of account deletion. Test: `functions/src/analytics.emulator-spec.ts` ("multiple pages", "versus revoke serializes").

### 3.4 Account deletion request ordering and ownerless result aggregates

`requestAccountDeletion` (`functions/src/account-deletion-service.ts:161-217`) records `ACCOUNT_DELETION_REQUESTED` *before* revoking analytics consent, then revokes and purges immediately afterward, in that exact order:

1. The request is persisted, capturing `analyticsResultEligible = hasActiveAnalyticsConsent(consentSnapshot)` from the live `consents/analytics` document read in the same transaction as the request write (`functions/src/firestore-account-deletion-store.ts:114-124`). This is a one-time, consent-at-request snapshot, not a value re-checked later.
2. If eligible, `ACCOUNT_DELETION_REQUESTED` is recorded through the normal per-user `users/{uid}/analyticsEvents` path (`dependencies.analytics(...)`, `functions/src/account-deletion-service.ts:190-199`), while consent is still granted.
3. Only in the `finally` block after that attempt does `dependencies.analyticsDeletion.revokeForAccountDeletion` run (`functions/src/account-deletion-service.ts:209-215`), which revokes analytics consent and immediately purges the owner's `analyticsEvents` (section 3.3). This ordering means the request event is never blocked by the revoke it triggers, and the revoke's immediate purge can never race ahead of the request recording.

The later terminal outcomes, `ACCOUNT_DELETION_COMPLETED` and `ACCOUNT_DELETION_FAILED`, are recorded by `recordOwnerlessResult` (`functions/src/firestore-account-deletion-store.ts:379-402`), which does not use `users/{uid}/analyticsEvents` at all. It writes into a single ownerless daily counter document, `analyticsDailyAggregates/{utcDate}` (`utcDate`, `functions/src/firestore-account-deletion-store.ts:543`), merging `counts.{eventName}` with `FieldValue.increment(1)`. That document's full field set is `schemaVersion`, `date`, `counts`, `updatedAt`, `expiresAt`. It carries no `uid`, `requestId`, session, or operation identifier of any kind, so a completed or failed deletion can be counted without ever re-identifying the account it happened to. Recording is gated by the same `analyticsResultEligible` snapshot captured at request time (`functions/src/firestore-account-deletion-store.ts:386-389`) and deduplicated per claim generation via `analyticsRecordedResultKeys` (`functions/src/account-deletion-contract.ts:62`), so a retried claim cannot double-count. `analyticsDailyAggregates` is unreachable by any client: it matches only the Firestore catch-all `match /{document=**} { allow read, write: if false; }` (`firestore.rules`, final block).

## 5. Minimization, owner isolation, out-of-scope

### 5.1 Minimization

- Every analytics event is exactly `schemaVersion` + `eventId` + `eventName` + `consentRevision` on the wire (section 1). The server adds only what it can independently authenticate or compute (owner from the auth token, `occurredAt`/`expiresAt`). `analyticsEventInputSchema` is `.strict()` and `StoredEvent` is validated with `hasExactKeys` (`functions/src/firestore-analytics-store.ts:565-591`), so no client-supplied free-form field can reach storage; this is enforced structurally, not by redaction after the fact.
- No event name encodes a value (there is no `plant_name_identification_requested` style event); values belong to Firestore domain documents, never to analytics.

### 5.2 Owner isolation

- Every analytics record is scoped to a single owner derived server-side from `request.auth.uid`, never client-asserted (`assertOwner`, `functions/src/analytics.ts:233-238`), mirroring `owns(uid)` / `accountMutable(uid)` checks enforced for every other per-user collection (`firestore.rules:404-431`).
- Consent state is a single per-owner document (`users/{uid}/consents/analytics`), the same shape as the pre-existing `consents/location`.
- `App Check` (`enforceAppCheck: true`) gates `getAnalyticsConsent`, `setAnalyticsConsent`, and `recordAnalyticsEvent` exactly like every other exported `onCall`/`onMutationCall` in `functions/src/index.ts:247-1029`; test: `firebase-tests/test/functions-smoke.cjs` ("missingAppCheck.status").
- `analyticsEvents`, `analyticsConsentOperations`, and `accountDeletionTombstones` are unreachable by any client read/write path (section 2); they exist only via the trusted Admin SDK used by Cloud Functions.

### 5.3 Out of scope (no third-party SDK, dashboard, ads, or segmentation)

Per the plan's Must-NOT-have list (`.omo/plans/android-app-implementation.md` Scope section) and Todo17's own text:

- No third-party analytics SDK (Firebase Analytics/GA4, Amplitude, Mixpanel, or any vendor SDK). The event pipeline is first-party Functions + Firestore only; `firebase-tests/test/data-safety-contract.test.cjs` ("first-party analytics has no vendor SDK dependency") asserts `functions/package.json` and `gradle/libs.versions.toml` contain no `firebase-analytics`, `amplitude`, or `mixpanel` dependency.
- No third-party dashboard or BI tool integration.
- No advertising SDK, ad attribution, or ad-ID collection.
- No user segmentation, cohorting, or behavioral profile built from analytics events for targeting. Events exist for product-metric aggregation only (PRD "핵심 지표" list), not per-user profiling beyond what the domain data (plants, watering, mini-home) already stores for the product's own functionality.
